## Public architecture evidence

### 1. Android native-library boundary

Android documents that native shared-library accessibility is package/application scoped. The `<uses-native-library>` mechanism makes a vendor-provided native library accessible to an application; it is not documented as a general cross-process attachment mechanism.

Reference: https://developer.android.com/guide/topics/manifest/uses-native-library-element

AOSP compatibility requirements also define application UID/process isolation as part of the Android security model.

Reference: https://source.android.com/docs/compatibility/17/android-17-cdd

Classification: **CONFIRMED** for the platform model.

### 2. Public Android Minecraft native-forwarder architecture

KafkaLauncher is a public proof-of-concept for Minecraft Bedrock Android 1.21.51.02. Its documentation describes a hosted-process architecture in which Minecraft Java/native components are run through the launcher process and a native forwarder is used around the Minecraft native entry point.

Reference: https://github.com/EnderNebula/KafkaLauncher

This demonstrates that a researcher-controlled alternative process/package architecture has existed publicly for a specific Minecraft version. It does **not** prove that the same architecture applies to Minecraft 1.26.45.1, nor does it prove a RenderDragon hook point.

Classification: **CONFIRMED as public historical architecture evidence; NOT CONFIRMED for the current target**.

### 3. Public RenderDragon shader/material evidence

The public `mcbe-shader-codebase` repository states that it contains vanilla Bedrock GLSL and reconstructed BGFX SC shader code generated from material.bin data extracted from Android Minecraft versions.

Reference: https://github.com/veka0/mcbe-shader-codebase

This is evidence that Android Minecraft material data can be studied at the shader/material layer. It does not expose the production native frame-submission call chain and therefore cannot identify a safe PVR integration point by itself.

Classification: **CONFIRMED for shader/material evidence; UNKNOWN for native submission path**.

### 4. Public Android RenderDragon shader-loader ecosystem

Multiple public shader projects document Android workflows involving a loader or modified Minecraft package for RenderDragon material loading. These demonstrate that Android RenderDragon customization exists in practice, but they do not establish a universal native hook point for the current Minecraft target.

Classification: **PROBABLE supporting context; insufficient for target-call-chain confirmation**.

## Evidence interpretation

The combined evidence supports the following bounded conclusion:

1. Minecraft Android has a substantial native runtime centered on `libminecraftpe.so`.
2. Android's normal application model does not provide a generic package-independent native-library attachment mechanism.
3. Public Minecraft Android projects have used controlled package/process architectures to study or extend native behavior for specific versions.
4. Public RenderDragon material/shader projects expose useful renderer-facing artifacts, but they do not establish the current production native frame/submission path.
5. Therefore the exact RenderDragon frame/render boundary for Minecraft `1.26.45.1` remains **UNKNOWN**.

## What remains to be established

The following are still unresolved:

- exact native module/thread responsible for the relevant rendering path;
- observable renderer lifecycle boundary;
- relationship between that boundary and BGFX command recording/submission;
- backend-specific execution path and presentation boundary;
- whether any legitimate researcher-controlled integration environment can expose those boundaries without modifying the retail process through an unauthorized mechanism.
