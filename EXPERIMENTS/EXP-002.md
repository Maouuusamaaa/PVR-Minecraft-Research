# EXP-002 — Target Detection

## Status

**IN PROGRESS — BASELINE CONFIRMED; RENDER TARGET UNKNOWN.**

EXP-001 is formally closed at the Minecraft loading boundary. EXP-002 is now active under the revised observation-first scope and does not assume that the PVR bridge executes inside retail Minecraft.

## Objective

Identify and characterize the relevant native/runtime target associated with Minecraft Bedrock Android rendering using only observable, authorized, reproducible evidence and public architectural sources.

The experiment must establish which native module(s), thread/path, and observable runtime boundary are relevant before any claim is made about PVR execution, RenderDragon interception, BGFX submission, or renderer replacement.

## What changed from the original gate

The original EXP-002 design assumed that native execution would first be established inside the Minecraft process. That assumption is no longer required because EXP-001 reached a formal `BLOCKED / NOT TESTED` target boundary.

The revised experiment therefore starts with target inventory and observation. A successful result does not require loading the PVR bridge into Minecraft.

## Research questions

1. Which native modules are observable through normal package/runtime metadata?
2. Which module(s) can be associated with Minecraft's native runtime without assuming a renderer hook point?
3. What renderer-related lifecycle or thread evidence is observable through legitimate tooling?
4. Which parts of the public RenderDragon/BGFX architecture can be mapped to those observations with reasonable confidence?
5. Which critical edges remain UNKNOWN because the production call chain is not observable from the available boundary?

## Public-source comparison

Public projects and documentation may be used to generate candidate architecture hypotheses, but they must not be treated as proof of the production implementation for Minecraft `1.26.45.1`.

Current evidence includes:

- public Android native-forwarder architecture in KafkaLauncher for Minecraft `1.21.51.02`;
- public Android Minecraft shader/material evidence from reconstructed RenderDragon/BGFX shader repositories;
- public Android RenderDragon shader-loader workflows;
- Android platform documentation defining package-scoped native-library accessibility and application process isolation.

These sources establish useful architectural context but do not identify the exact native RenderDragon frame/submission call chain for the current target.

## Evidence model

Record each observation using one of:

- CONFIRMED — directly supported by source/runtime evidence.
- TESTED — actually observed on the target environment.
- PROBABLE — technically plausible but not directly demonstrated.
- HYPOTHESIS — requires an experiment.
- BLOCKED — required observation cannot currently be performed.
- FAILED — attempted and unsuccessful.
- UNKNOWN — unresolved.

## Controlled observation plan

1. Freeze the exact Minecraft version and device context.
2. Record package, ABI, native-library inventory, process identity, and GPU information where normally observable.
3. Record the runtime/module boundary available without modifying the Minecraft process.
4. Identify candidate renderer-related components from observable metadata and public documentation.
5. Compare candidates against public RenderDragon/BGFX architecture only after target-side observations are recorded.
6. Correlate any candidate with lifecycle/thread/render timing when legitimate observation is available.
7. Record negative results and permission limitations explicitly.
8. Do not attempt unauthorized process modification, security-boundary bypass, stealth loading, or exploit-based instrumentation.

No proprietary Minecraft binary or extracted proprietary library should be committed to the research repository.

## Desired result

A reproducible target-detection record identifying at least one relevant native/runtime boundary, or a documented reason why the boundary remains UNKNOWN/BLOCKED.

A useful positive result should include:

- module/library identity;
- observation method;
- runtime timing/lifecycle;
- thread or execution context if observable;
- relationship to rendering based on evidence;
- confidence/status classification;
- remaining unknowns.

## Failure criteria

EXP-002 is considered FAILED if an attempted observation cannot reliably distinguish the rendering target from unrelated native components, or if the result depends on an unsupported assumption presented as fact.

A failure must include the environment, observation method, collected evidence, likely cause, and next step.

## Important boundary

Finding a native module is **not** equivalent to finding the RenderDragon submission point.

Finding a renderer-related symbol is **not** equivalent to proving that it is the production BGFX submission function.

Finding a BGFX-related code path is **not** equivalent to proving that PVR can safely replace or intercept it.

Those claims require separate evidence.

## Current result

EXP-002 is not complete. The next legitimate research step is to improve the observation boundary using information available from the installed package/runtime and public source evidence, while preserving the current UNKNOWN classification until direct evidence supports a stronger conclusion.
