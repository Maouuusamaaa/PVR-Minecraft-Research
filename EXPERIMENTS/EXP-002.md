# EXP-002 — Target Detection

## Status

**NOT STARTED — research/design phase documented.**

No target-device runtime observation has been performed yet. This document defines the evidence boundary and the controlled objective for the next experiment.

## Objective

Identify the relevant native/runtime target associated with Minecraft Bedrock Android rendering without assuming that a function name, library name, or public project hook is identical to the production implementation.

The experiment must establish which native module(s), thread/path, and observable runtime boundary are relevant before any attempt is made to invoke PVR from the Minecraft render path.

## Why EXP-002 follows EXP-001

EXP-001 asks the smallest question: can a controlled native bridge initialize in the target Minecraft process?

EXP-002 asks the next question: once native execution is established, what runtime target actually corresponds to the rendering path we need to study?

The project must not jump directly from successful library loading to a presumed RenderDragon hook.

## Confirmed external evidence

- Public MaterialBinLoader documents an Android ARM/ARM64 native-library dependency approach involving `libminecraftpe.so`.
- Public KafkaLauncher documents a different Android native-forwarder architecture around the Minecraft native library and native activity entry point.
- Public BetterRenderDragon has an Android build configuration using an Android preloader dependency, while its Windows build has a separate renderer-hooking dependency set.
- These projects demonstrate public native integration patterns, but they do **not** establish the exact production RenderDragon call chain for the target Minecraft version/device.

## Hypothesis

The useful target will likely be located within or adjacent to the Minecraft native renderer/runtime module and will expose an observable boundary around frame construction, render-pass generation, command recording, submission, or backend execution.

This is a **HYPOTHESIS**, not a confirmed fact.

## Evidence model

Record each observation using one of:

- CONFIRMED — directly supported by source/runtime evidence.
- TESTED — actually observed on the target environment.
- PROBABLE — technically plausible but not directly demonstrated.
- HYPOTHESIS — requires an experiment.
- BLOCKED — required observation cannot currently be performed.
- FAILED — attempted and unsuccessful.
- UNKNOWN — unresolved.

## Controlled observation plan

1. Record the exact Minecraft Bedrock version used for the experiment.
2. Record Android version, ABI, device model, and available GPU identification.
3. Establish the native-process/module boundary visible during a normal Minecraft launch.
4. Identify candidate renderer-related modules or runtime objects from observable evidence.
5. Correlate candidates with public RenderDragon/BGFX architecture only after collecting target-side evidence.
6. Determine whether the candidate is loaded before or during rendering and whether it is associated with the render thread/path.
7. Preserve logs and observations even when no useful target is found.

No proprietary Minecraft binary or extracted proprietary library should be committed to the research repository.

## Desired result

A reproducible record that identifies at least one relevant native/runtime target and explains why it is considered relevant, including:

- module/library identity;
- observation method;
- runtime timing/lifecycle;
- thread or execution context if observable;
- relationship to rendering based on evidence;
- confidence/status classification;
- remaining unknowns.

## Failure criteria

EXP-002 is considered FAILED if an attempted observation cannot reliably distinguish the rendering target from unrelated native components. A failure must include the environment, observation method, collected evidence, likely cause, and next step.

## Important boundary

Finding a native module is **not** equivalent to finding the RenderDragon submission point.

Finding a renderer-related symbol is **not** equivalent to proving that it is the production BGFX submission function.

Finding a BGFX-related code path is **not** equivalent to proving that PVR can safely replace or intercept it.

Those claims require separate evidence.

## Next experiment

If EXP-002 produces a sufficiently reliable target, proceed to **EXP-003 — Frame/Render Reachability**, whose objective is to prove that the controlled bridge can observe or execute on a render/frame-related path.
