# EXP-001 — Native Library Loading

## Objective

Determine whether a controlled native bridge/library can be loaded into a Minecraft Bedrock Android process without assuming a specific RenderDragon symbol or renderer hook.

## Status

**CONTROLLED ANDROID RUNTIME CHECKPOINT CONFIRMED; MINECRAFT TARGET NOT TESTED.**

The bridge has now been built for Android ARM64, packaged in a signed Android harness, installed on the user's Android 13 device, loaded by the Android runtime in the controlled harness process, and observed emitting `PVR_BRIDGE_LOADED`. This proves the lower-level Android native-loading path for the bridge.

It does **not** prove loading into Minecraft. The target Minecraft process still requires an authorized, reproducible and reversible loading method and target-side PID/process evidence.

Runtime evidence is recorded in [`EXP-001-HARNESS-RUNTIME-2026-09-15.md`](EXP-001-HARNESS-RUNTIME-2026-09-15.md).

### Controlled Android runtime

The signed harness APK was installed with Android's package manager and returned `Success`. The package manager subsequently listed `com.pvr.exp001.harness`.

The harness was launched as package `com.pvr.exp001.harness`. Logcat then recorded the bridge constructor, PID/TID, the required marker, initialization completion, and the explicit initialization call:

```text
PVR-Bridge: Bridge constructor running
PVR-Bridge: Process ID (PID): 8936
PVR-Bridge: Thread ID (TID): 8936
PVR-Bridge: MARKER: PVR_BRIDGE_LOADED
PVR-Bridge: Bridge initialization complete
PVR-Bridge: bridge_initialize() called explicitly
```

Therefore:

```text

PVR_BRIDGE_LOADED = CONFIRMED
bridge_initialize() = CONFIRMED
```

The full device evidence is recorded separately in `EXP-001-HARNESS-RUNTIME-2026-09-15.md`.

## What This Experiment Does NOT Prove

- It does not prove compatibility with the user's installed Minecraft version.
- It does not prove that the bridge can be loaded into Minecraft.
- It does not prove that RenderDragon code can be reached.
- It does not prove that a render-thread callback can be obtained.
- It does not prove that PVR can execute inside Minecraft.
- It does not prove GPU work or renderer modification.

## Target Minecraft Test

The target-side success criterion remains a reproducible native initialization event from the controlled bridge **inside the target Minecraft process**, with the exact Minecraft version, Android version, ABI, package/process identity, PID/TID, loading method, library path, timestamp and unedited logcat evidence recorded.

The repository currently does not contain a legitimate, reproducible loading mechanism for placing the bridge into the installed Minecraft process. Public Android native-loading projects remain architectural references only and do not establish compatibility with the user's installed target.

If an authorized and reversible target-side loading method is unavailable, the Minecraft portion must remain `BLOCKED`/`NOT TESTED` rather than being inferred from the harness result.
