# EXP-001 — Native Library Loading

## Objective

Determine whether a controlled native bridge/library can be loaded into a Minecraft Bedrock Android process without assuming a specific RenderDragon symbol or renderer hook.

## Status

NOT STARTED — the target-device runtime experiment has not yet been executed.

The reproducible runtime procedure and evidence requirements are documented in
[`EXP-001-RUNTIME-TEST.md`](EXP-001-RUNTIME-TEST.md). A controlled Android test
harness, if used, must be treated separately from loading into Minecraft.

## Evidence Collected Before Runtime Test

### CONFIRMED — native library dependency injection is a documented public technique

MaterialBinLoader documents modifying `libminecraftpe.so` with `patchelf --add-needed` so that a custom ARM/ARM64 native library is loaded alongside Minecraft's native library. It explicitly documents separate 32-bit and 64-bit libraries and an Android NDK build path.

This proves that a public project has used a native-library loading mechanism against the Minecraft Android native library. It does not prove that the same mechanism works with the user's current Minecraft version or Android 13 device.

Source: ddf8196/MaterialBinLoader README.

### CONFIRMED — Android ARM64 target is directly relevant

MaterialBinLoader explicitly provides an ARM64 (`arm-v8a`) library path. This matches the project's intended Android ARM64 research target.

### CONFIRMED — newer public Android launcher research shows another loading/forwarder architecture

KafkaLauncher documents an Android launcher approach where a forwarder `libminecraftpe.so` is loaded by Android, locates the already mapped real Minecraft library through `/proc/self/maps`, resolves the native activity entry point, installs hooks, and then calls the original entry point.

This is architectural evidence for an alternative native-loading/hooking model. It is not evidence that this exact implementation should be used for the PVR project.

## What This Experiment Does NOT Prove

- It does not prove compatibility with the user's installed Minecraft version.
- It does not prove that a library can be loaded on the user's device.
- It does not prove that RenderDragon code can be reached.
- It does not prove that a render-thread callback can be obtained.
- It does not prove that PVR can execute inside Minecraft.
- It does not prove GPU work or renderer modification.

## Proposed Controlled Test

1. Record the exact Minecraft Bedrock version and ABI.
2. Build a minimal ARM64 native bridge containing only a startup marker/logging entry point.
3. Use a controlled, reversible test environment rather than modifying the production installation blindly.
4. Launch Minecraft and collect native process logs.
5. Confirm whether the bridge initialization marker appears.
6. If loading succeeds, record the result as TESTED and preserve the exact environment.
7. If loading fails, record the failure, error/log evidence, likely cause and next experiment rather than treating it as a project failure.

## Success Criterion

A reproducible native initialization event from the controlled bridge inside the target Minecraft process, with the Minecraft version, Android version, ABI and evidence recorded.

## Next Experiment

If EXP-001 succeeds: proceed to EXP-002 — Target Detection.

If EXP-001 fails: diagnose the loading boundary first; do not jump directly to RenderDragon function interception.

## Research Boundary

No proprietary Minecraft APKs, Mojang native libraries, extracted proprietary binaries, or copyrighted binary assets are committed to the research repository. Only source, documentation, experiment notes, scripts and configuration belong here.
